# Roadmap Mirocraft

Каждая задача рассчитана примерно на одну сессию Claude Code.
Формат работы: «Прочитай CLAUDE.md, docs/ARCHITECTURE.md и выполни задачу X.Y из ROADMAP».
После завершения задачи — отметить [x] и закоммитить.

## Фаза 1 — Ядро демона

- [x] 1.1 Хранилище: SQLite (modernc.org/sqlite), миграции, репозитории users/servers/tokens,
      юнит-тесты на репозитории
- [x] 1.2 Интерфейс Runner + ProcessRunner (Linux): запуск/остановка/kill java-процесса,
      чтение stdout в кольцевой буфер + broadcast подписчикам, отправка команд в stdin,
      корректная остановка через команду `stop` с таймаутом и fallback на kill
- [x] 1.3 Реестр CoreProvider + первые провайдеры: Vanilla (Mojang manifest) и Paper
      (PaperMC API) с проверкой SHA, кэш скачанного, определение требуемой Java по версии MC.
      Две поправки к реальности, выявленные прогоном по живым API:
      PaperMC v2 отключён (410 sunset), актуальный — fill.papermc.io/v3 с другой
      формой ответа; Minecraft перешёл с 1.x на календарные версии начиная с 26.1
      и требует Java 25. Есть тесты с тегом `live` — они ходят в настоящие API
      и скачивают настоящий jar, чтобы такие расхождения ловились
- [x] 1.4 Менеджер Java (для ProcessRunner): скачивание Temurin нужной версии под ОС/арх,
      распаковка, реестр установленных рантаймов.
      Ставится JRE, а не JDK — вчетверо меньше, а сервер только запускает Java.
      Нужны четыре версии: 8, 17, 21, 25. Плюс internal/daemon.Provisioner —
      он связывает 1.2, 1.3 и 1.4: перед стартом кладёт ядро в каталог сервера
      и поднимает нужный рантайм. Проверено на живом Paper 1.21.4
- [x] 1.5 DockerRunner: контейнер на сервер, лимиты RAM/CPU, тома, стрим логов,
      attach для команд; автовыбор Runner при старте.
      Клиент Docker API написан свой (internal/docker): официальный SDK тянет
      около сотни пакетов ради шести эндпоинтов, а обещание проекта — один
      небольшой файл. Вывод контейнера приходит кадрами с 8-байтовым
      заголовком, без демультиплексирования длины врезались бы прямо в лог.
      Память ограничена с запасом сверх -Xmx: JVM живёт и вне кучи, и лимит
      вровень с ней — OOM-kill в первый же нагруженный день.
      На Linux контейнер идёт от пользователя демона: иначе всё, что сервер
      пишет в примонтированный каталог, принадлежит root, и файловый менеджер
      панели показывает файлы, которые не может изменить.
      Контейнер переживает свой демон, поэтому при старте демон усыновляет
      свои контейнеры по метке — иначе запущенный сервер показывался бы
      остановленным и не запускался бы снова, потому что имя занято. Время
      старта берётся у контейнера, чтобы усыновлённый сервер не сообщал
      нулевой аптайм.
      Явное runner.type: docker соблюдается строго: молча получить процессы
      вместо запрошенных контейнеров значит работать не в той конфигурации и
      не иметь способа это заметить. При Docker JRE на хост не качается.
      Проверено на живом Docker и настоящем Paper 1.21.4: контейнер поднялся,
      мир загрузился, команда из панели дошла до сервера, метрики пришли из
      docker stats, игроки — пингом через опубликованный порт; демон убит
      жёстко и после перезапуска усыновил свой контейнер вместе с консолью.
- [x] 1.6 ProcessRunner на Windows: job objects, пути, тест кросс-компиляции.
      Job object на Windows и process group на Unix за одним интерфейсом —
      убийство сервера достаёт до всего дерева, а не до прямого потомка.
      Проверено на живом Paper: до этого в системе нашёлся java.exe с прошлого
      запуска, переживший свой демон на два часа и державший session.lock, —
      из-за него сервер не стартовал с ошибкой про заблокированный файл.
      После правки жёсткое убийство демона забирает JVM с собой.
      Раз демон теперь уносит серверы за собой, Shutdown сначала штатно их
      останавливает: иначе выход демона ронял бы миры без сохранения.
      Пути: os/exec разрешает относительный путь исполняемого файла не
      относительно Cmd.Dir, а относительно рабочего каталога вызывающего
      процесса. Демон отдавал относительный путь к java (data_dir по умолчанию
      относительный), и запуск падал с «не удаётся найти указанный путь»,
      называя путь, который существует. Теперь пути разрешаются в абсолютные.
      Кросс-компиляция стала тестом: половина кода пакета невидима компилятору,
      который прогонял тесты, поэтому сборка под все цели — единственный способ
      это заметить. Проверено, что тест действительно падает на поломке в
      unix-ветке с Windows-машины.

## Фаза 2 — API

- [x] 2.1 Каркас API: роутер, middleware (auth, logging, rate limit), эндпоинты
      /auth/login, /users (admin), выдача и отзыв токенов.
      Плюс: bootstrap первого админа со сгенерированным паролем при пустой базе,
      аудит-лог на мутирующих действиях, эндпоинты тем (/themes, /users/me/themes)
      с валидацией импорта — бэкенд под 3.7/3.8
- [x] 2.2 Эндпоинты серверов: CRUD, start/stop/restart/kill, статус с метриками
      (RAM, uptime, игроки). Игроки берутся не query-протоколом, а Server List
      Ping (internal/mcping): query требует enable-query в server.properties,
      а list ping работает на игровом порту без настройки. TPS через ping
      недоступен — появится позже через плагин или лог-парсинг.
      Заодно сделан Tasks API (часть 2.7): power-операции возвращают task_id
- [x] 2.3 WebSocket консоли: стрим логов + отправка команд, история последних 500 строк
- [x] 2.4 Файловый API: список/чтение/запись/загрузка/удаление в пределах директории
      сервера, защита от path traversal, лимит размера, тесты на traversal — обязательны.
      Песочница вынесена в отдельный пакет internal/fileman — одно место, где
      клиентский путь превращается в реальный, и его можно закрыть тестами целиком.
      Побочно вскрылось: путь к каталогу сервера хранился абсолютным, поэтому
      перенос каталога данных осиротил бы все серверы. Теперь выводится
- [x] 2.5 Бэкапы: создать/список/восстановить/скачать, расписание.
      Перекачиваемое (ядро, libraries, versions, кэши) в архив не попадает —
      236 МБ каталога дают 23 МБ бэкапа, а восстановление ничего не теряет,
      потому что запуск всё это заново провизионит. Перед архивацией живого
      сервера ему отправляется save-off + save-all flush, после — save-on.
      Нечитаемые файлы (session.lock живого сервера) пропускаются, а не валят
      бэкап. Расписание — cron с ретенцией, планировщик тикает и переживает
      простой демона: пропущенный запуск делается на следующем тике
- [x] 2.6 Игроки и настройки: эндпоинты players/whitelist/ops, settings со схемой
      server.properties, kick/ban через консольные команды.
      Списки читаются из JSON-файлов сервера, а не из вывода консоли: консоль —
      человекочитаемый лог, чьи формулировки меняются между версиями и форками.
      Имя игрока валидируется строго (3–16, [a-zA-Z0-9_]) — это не аккуратность,
      а граница безопасности: имя попадает в консольную команду. Онлайн-список
      берётся из sample в list ping и честно помечается неполным.
      server.properties читается и пишется с сохранением комментариев, порядка
      и незнакомых ключей — иначе редактор ломал бы моды
- [x] 2.7 Асинхронщина и события: Tasks API, WebSocket-шина /events,
      webhooks с HMAC-подписью и ретраями.
      Одна шина, два потребителя — панель по сокету и вебхуки по HTTP: обе
      стороны хотят одних и тех же фактов, поэтому не стали растить каждой
      фиче свой канал уведомлений. Публикация не блокируется: очередь на
      подписчика 128 событий, дальше события отбрасываются — залипшая вкладка
      браузера не должна тормозить раннер, который это событие породил.
      Вебхук получает URL от пользователя, а запрос делает демон — это форма
      SSRF, поэтому loopback, приватные и link-local адреса отвергаются, пока
      оператор не включит их осознанно (webhooks.allow_private_hosts).
      Побочно закрыта дыра: эндпоинты вебхуков были защищены только
      аутентификацией, и read-only токен мог зарегистрировать исходящий хук.
      Теперь чтение — servers:read, регистрация и удаление — servers:write.
- [x] 2.8 Scheduler: cron-задачи с цепочками действий (command/power/backup).
      К трём типам добавлен wait: без паузы документированный пример
      «ежедневный рестарт с предупреждением игрокам» неисполним —
      предупреждение и остановка ушли бы одной строкой.
      Цепочка обрывается на первой ошибке: не сумевшая предупредить не должна
      всё равно останавливать сервер.
      Составить цепочку требует скоупов её действий, а не только
      servers:write — иначе право «менять сервер» стало бы правом выполнять
      произвольные команды консоли, и скоупы перестали бы что-либо значить.
      Заодно вскрылось, что список маршрутов в регрессе не догнал 2.7:
      эндпоинты вебхуков и шины в нём отсутствовали, теперь он проверяет все.
- [x] 2.9 OpenAPI: openapi.yaml, Swagger UI на /api/docs, сверка контракта.
      Без oapi-codegen, и это осознанно: API уже написан руками и работает,
      а ретрофит генерации переписал бы все хендлеры ради нулевой выгоды.
      Контракт делает обязательным не кодоген, а тест: маршруты роутера и
      пути спецификации сверяются в обе стороны, плюс проверяются имена
      path-параметров, теги, summary и разрешимость всех $ref. Спецификация,
      которую никто не сверяет, расходится с кодом за один релиз.
      Swagger UI вшит в бинарник, а не подтягивается с CDN: страница
      документации, работающая только при доступе в интернет, — ровно та
      зависимость, ради отсутствия которой всё складывается в один файл, а
      сторонний скрипт на странице — ещё одна сторона, способная выполнять код
      в браузере администратора. E2E раскрывает все группы в настоящем
      браузере: спеку, которую Swagger UI не смог отрисовать, Go-тесты не
      поймают.

## Фаза 3 — Веб-панель

- [x] 3.1 Каркас: Vite + React + Tailwind, роутинг, логин, хранение токена,
      клиент API с типами, go:embed продакшен-сборки.
      Сюда же — слой токенов тем: web/src/themes/tokens.css с полным контрактом
      CSS-переменных, маппинг цветов Tailwind на var(--...), ESLint-правило
      «никаких цветовых литералов в компонентах» в CI. Делается до компонентов,
      иначе цвета расползутся по коду и придётся вычищать.
      Сделано без ESLint: проверка литералов — отдельный скрипт
      web/scripts/check-color-literals.mjs (не нужен ни ESLint, ни написание
      плагина, а проверяет ровно одно). Плюс палитра Tailwind заменена целиком,
      поэтому bg-gray-900 просто не компилируется — правило держит сборка,
      а не ревью
- [x] 3.2 Список серверов + создание (форма: ядро → версия → RAM; порт
      назначается автоматически, мастер по шагам — позже)
- [x] 3.3 Страница сервера: консоль (WebSocket), кнопки управления, метрики.
      Подсветка уровней лога — только через --console-* переменные
- [x] 3.4 Файловый менеджер + редактор server.properties с подсказками.
      Страница сервера стала вкладочной; консоль при переключении не
      размонтируется, а прячется: она держит вебсокет и историю, и заглянуть
      в файлы значило бы молча потерять лог падающего сервера.
      В редакторе настроек знакомые ключи получают контрол по своему типу и
      пояснение, незнакомые — текстовое поле: форк или мод заводит ключи
      свободно, и прятать нераспознанное значит терять их при первом
      сохранении. Ключи, которыми управляет панель, — только для чтения.
      Попутно вскрылось расхождение в API: чтение отдавало {values, schema,
      managed}, а запись — {values, restart_required}, поэтому клиент после
      сохранения оставался без схемы и страница настроек гасла. Теперь запись
      отвечает тем же, что чтение, плюс restart_required — и это закрыто
      тестом. Проверено в настоящем браузере против живого демона.
- [x] 3.5 Каталог плагинов/модов: поиск по Modrinth API, установка в один клик.
      Modrinth — единственный из трёх крупных источников с документированным API
      без ключа: CurseForge требует ключ на каждую установку, чего self-hosted
      панель раздать не может, а у SpigotMC API нет вовсе.
      Формы ответов сняты с живого API, а не угаданы, и это окупилось: Modrinth
      называет плагины тоже `mod`, а загрузчик в поиске лежит в `categories`, а
      не в отдельном фасете.
      Загрузчик берёт от ядра: core.Provider теперь сам говорит, что принимает.
      У vanilla — ничего, и установка на него отвергается с объяснением: jar
      рядом с ним никогда не будет прочитан.
      Ставятся только обязательные зависимости. Версия по умолчанию — новейший
      релиз, а не новейшая вообще. Скачанное сверяется с контрольной суммой и
      пишется через временный файл.
      Живая проверка нашла настоящий баг: песочница отдаёт свою ошибку
      «уже существует», а установка сверялась с os.ErrExist — из-за чего падала
      на любом сервере, который хоть раз запускался. Закрыто тестом.
- [x] 3.6 Бэкапы + настройки сервера, админка пользователей.
      Вкладка бэкапов опрашивает список, только пока что-то снимается, —
      простаивающая вкладка молчит. Восстановление требует ввести RESTORE и
      выключено, пока сервер запущен: API его всё равно отвергнет, а сказать
      об этом заранее лучше, чем дать клику провалиться.
      Параметры сервера отделены от server.properties, хотя для оператора и
      то и другое «настройки»: эти меняют команду запуска, а не файл, который
      читает игра.
      В админке блокировка и снятие админа у себя самого просто не
      предлагаются — это выход из панели, в которой стоишь.
      Проверено на живом мире: бэкап настоящего сервера снялся, расписание
      сохранилось, учётная запись создалась, заблокировалась и удалилась.
- [x] 3.7 Встроенные темы и переключение: файлы тем dark, light, midnight, grass,
      nether (каждая — один css-файл, только переопределение переменных);
      реестр тем с метаданными; селектор в настройках профиля + тумблер
      тёмная/светлая в шапке; режим `system` (prefers-color-scheme) как дефолт
      для новых пользователей; хранение выбора в профиле на сервере
      (поле `theme` в /users/me) + localStorage-кэш; инлайн-скрипт в index.html
      для применения темы до первого рендера (тест на отсутствие FOUC);
      автотест контраста WCAG AA по всем темам и всем парам токенов
- [x] 3.8 Редактор кастомных тем: выбор базы (dark/light), акцентный цвет и радиус
      скруглений через контролы, живое превью, сохранение своей темы в профиль;
      экспорт/импорт JSON (schema mirocraft.theme/v1) с валидацией — whitelist
      имён переменных, только цвета и длины в значениях, прогон импорта через
      проверку контраста с предупреждением о непрошедших парах

## Фаза 4 — Установщики и DNS/SSL

- [x] 4.1 internal/dns: интерфейс DNSProvider + реализации deSEC, DuckDNS, Cloudflare;
      мини-DynDNS в демоне (обновление записей при смене IP); SRV для Java-серверов.
      Возможности провайдера объявлены явно: DuckDNS не умеет SRV, и панель,
      которая делала бы вид, что умеет, дала бы сервер на нестандартном порту,
      до которого нельзя достучаться по имени, — причём ничего не выглядело бы
      сломанным.
      Внешний адрес спрашивается у трёх независимых источников, решает
      большинство: один ошибшийся или перехваченный источник увёл бы все
      серверы панели на чужой адрес.
      Метод назван EnsureAddress, а не EnsureA как в ARCHITECTURE: он пишет и
      AAAA, а имя, которое иногда лжёт, стоит кому-то полдня.
      **Живой проверки провайдеров нет** — она требует настоящего домена и
      токенов. Проверены вживую только источники внешнего адреса (все три
      сходятся). Провайдеры покрыты заглушками, повторяющими документированные
      формы ответов; перед релизом их нужно прогнать на настоящем домене.
      Побочно вскрылась настоящая дыра: PATCH /servers/{id} никогда не
      принимал порт, поэтому вкладка «Параметры» из 3.6 показывала поле,
      отвечала «Сохранено» и молча ничего не меняла. Спека при этом утверждала,
      что порт менять можно. Закрыто тестом, добавлена проверка занятости.
- [x] 4.2 Сертификаты: ACME HTTP-01, DNS-01 через DNS-провайдера, self-signed,
      автопродление.

      потому что это лаунчер, он докачивает сервер при первом запуске. Это
      записано в модель (Build.Artifact), потому что меняет обещания панели:
      первый старт такого сервера требует интернета, а проверка размера,
      написанная под серверный jar, отвергает лаунчер. Проверено запуском:
      Fabric поднялся, мир создался, «Done (8.109s)».
      Все три проверены запуском на этой машине: установщик отработал, сервер

- [x] 6.2 CoreProvider'ы: Spigot (BuildTools с кэшем), Sponge, Mohist, Arclight.

      не запустив. Первая, мелкая: на Windows BuildTools скачивает свой

- [x] 6.3 Прокси: Velocity, BungeeCord, Waterfall — тип proxy, привязка серверов панели
      с автогенерацией конфигов forwarding
      Прокси — это сервер панели с ядром типа proxy. Отличий от обычного
      сервера три, и каждое ломает установку, если его не учесть.
      Первое: прокси не понимает `stop`, он останавливается по `end`. Команда
      теперь принадлежит серверу, а не раннеру: один раннер держит оба типа
      сразу, и не тот глагол превращает штатную остановку в убийство по
      таймауту — для Minecraft-сервера это откат мира.
      Второе: у прокси нет server.properties. Он читает velocity.toml или
      config.yml, и порт там пишется по-разному; файл свойств, который он
      никогда не откроет, оставил бы опубликованный панелью порт указывающим в
      никуда.
      Третье: Velocity версионируется сам по себе, а не по версии Minecraft, —
      таблица версий Java, читающая «3.5.1», выдаёт бессмыслицу. У провайдера
      появился свой способ сказать, какая Java нужна.
      Привязка: `PATCH /servers/{id}` принимает proxy_id. Панель сама пишет
      список бэкендов в конфиг прокси (адреса берутся из портов, которые она же
      и выдала), пишет `try` — без него прокси отвечает «нет доступных
      серверов», — выключает online-mode на бэкендах, потому что игрока уже
      проверил прокси, и следит за forwarding.secret у Velocity, никогда не
      перезаписывая существующий: его знают бэкенды, и новый закрыл бы вход всем.
      Чужой прокси привязать нельзя: это поставило бы ваш сервер на его адрес.
      Тест поймал мой баг в разборе YAML: флаг `s` в регулярном выражении
      заставил точку совпадать с переводами строк, и блок servers: съедал весь
      остаток файла вместе с listeners и timeout.
- [x] 6.4 Bedrock: BDS (нативный бинарник, UDP, отдельный stop), PocketMine-MP (+PHP-рантайм),
      Три ядра, три разных способа не быть Java-сервером, и каждый вскрыл
      что-то только при живом запуске.
      BDS — нативный бинарник в zip, а не jar: появились Artifact=archive и
      распаковка, а раннер научился запускать программу вместо JVM. Слушает
      UDP, поэтому контейнер публикует порт как UDP — как TCP он не принял бы
      никого. Образ тоже другой: в Java-образе нет C++-рантайма, а musl не
      загрузит его библиотеки, поэтому ubuntu.
      Лицензия Mojang запрещает перераспространение, поэтому качается у них —
      и вот тут выяснилось, что **их CDN отвергает наш User-Agent**: соединение
      рвётся посередине, и это приходит как внутренняя ошибка HTTP/2, то есть
      выглядит сетевым сбоем. Провайдер теперь может переопределить агент;
      менять его всем нельзя — PaperMC наоборот просит представляться.
      PocketMine — PHP, и не тот, что в дистрибутиве: он собирает свой с
      нужными расширениями, а на стоковом phar падает на отсутствующем
      расширении. Появился менеджер PHP-рантаймов по образцу Java-менеджера.
      Два капкана с путями: os/exec ищет голое имя в PATH, поэтому
      bedrock_server искался везде, кроме своего каталога; а путь интерпретатора
      абсолютный, и склейка его с каталогом сервера дала путь с двумя буквами
      диска. Теперь относительное склеивается, абсолютное — нет.
      И третий: phar клался под именем server.jar, под которым PHP его не
      находил — «Could not open input file».
      Проверено запуском всех трёх: BDS сообщил «Server started.» и слушает
      UDP 19132; PocketMine — «Done (2.03s)», версия 5.44.3; PowerNukkitX
      загрузил миры. При этом BDS не перезаписывает server.properties,
      allowlist и permissions при обновлении: это превратило бы обновление в
      сброс, и оператор узнал бы об этом, когда игроки не смогут зайти.
- [x] 6.5 Кроссплей-галочка: автоустановка Geyser+Floodgate на Java-сервер, UDP 19132,
      автоконфиг
      Галочка в настройках сервера: панель ставит Geyser и Floodgate под
      загрузчик этого ядра, выделяет UDP-порт и правит конфиг Geyser.

      отвергает игрока за отсутствие сессии Mojang — это читается как «кроссплей
      не работает», а не как «не хватает второго плагина».
      Порт по умолчанию 19132: его клиент пробует сам, без ввода адреса. При
      выключении галочки порт сохраняется — иначе повторное включение сменило бы
      адрес, который игроки уже записали.
      Контейнер публикует UDP рядом с игровым TCP, а не вместо: сервер с
      кроссплеем принимает Java-игроков по TCP и Bedrock — по UDP одновременно.
      Имена платформ у GeyserMC не совпадают с именами загрузчиков: плагин под
      Paper публикуется как spigot, а BungeeCord у Geyser пишется bungeecord, у
      Floodgate — bungee. Это таблица, считанная с их API, а не преобразование.
      Живая проверка на настоящем Paper: Geyser 2.11.1 и Floodgate 2.2.5
      установились, «Geyser запущен на UDP порту 19132», «Done (42.958s)», оба
      порта слушают. И вскрыла настоящее: секция в конфиге называется `java:`, а
      не `remote:` — мой переписыватель искал несуществующую и молча ничего не
      менял, из-за чего `auth-type` оставался `online`, и Bedrock-игрока просили
      бы войти под Java-аккаунтом. Ровно то, ради чего ставится Floodgate.
      Исправлено, проверено перезапуском: в конфиге `auth-type: floodgate`.
- [x] 6.6 Модпаки: установка .mrpack (Modrinth) в один клик, включая автоустановку
      нужного загрузчика.
      Отдельная вкладка, а не фильтр в каталоге дополнений: плагин к серверу
      добавляют, модпак сервер заменяет. Один вызов скачивает `.mrpack`, читает
      из индекса загрузчик, очищает каталог модов, ставит файлы пака и его
      `overrides/`, переключает сервер на нужное ядро и версию и сразу же ставит

      Загрузчик берётся из `modrinth.index.json`, а не из тегов версии: что пак
      объявляет зависимостями, то ему и нужно. Каталог модов очищается целиком —
      моды пака это весь список модов, и остаток от прошлой установки грузился бы
      вместе с ним. `client-overrides/` пропускаются, `server-overrides/`
      перекрывают `overrides/`, файлы с `env.server: unsupported` не скачиваются:

      Скачивание — только по https и только с хостов реестров: индекс пишет тот,
      кто выложил пак, и без списка это способ заставить панель сходить куда
      угодно, включая адреса изнутри сети оператора. Пути из архива и из индекса
      проходят проверку на выход за каталог, распаковка читается через
      `LimitReader`, а не по заявленному размеру.
      CurseForge — сознательно нет: их API требует ключ на каждую загрузку,
      а self-hosted панели неоткуда взять ключ для каждого оператора. Формат,
      который нельзя скачать, хуже честного «не поддерживаем»; это написано и в
      доках, и на самой вкладке.
      CI поймала то, что Windows-машина показать не может: `..\evil.jar` —
      выход за каталог на Windows и обычное имя файла на Linux, поэтому
      проверка пути отвечала по-разному в зависимости от того, где запущена
      панель. Теперь бэкслеш — разделитель везде, и `C:/x` отвергается на обеих
      системах. Добавлен `make test-linux` (тот же прогон, что в CI, в
      контейнере) — потому что этот баг доехал до master незамеченным.
      Заодно чинён тест процесс-групп: убитый на Linux процесс остаётся зомби,
      пока его не подберёт init, а `PidExists` считает зомби живым — проверка
      падала на том, что убийство как раз сработало.
      Проверено вживую на настоящем паке с Modrinth (Vanilla Perfected 1.0.3,
      Minecraft 26.2): из 112 файлов индекса на сервер встал 81 jar (клиентские

      «Loading 129 mods», «Done (9.585s)». Установка на запущенный сервер

      предлагали выставить панель наружу, и человеку, который ставит её на
      свой компьютер, выбирать было не из чего. Теперь `addr: 127.0.0.1`,
      `tls.mode: off` и никакого правила фаервола: трафик не покидает машину,
      шифровать его не от кого, а самоподписанный сертификат на localhost даёт
      только предупреждение браузера, которое человек приучается пролистывать.
      Порты самих серверов при этом открываются как раньше — режим прячет
      панель, а не серверы, и установщик об этом прямо говорит.

## Оформление

Переделано целиком 2026-08-11 по просьбе пользователя: «дизайн плохой».

- [x] **Оболочка** — постоянный сайдбар вместо текстовых ссылок в шапке.
      Раньше вся навигация лежала в одну строку, а контент болтался посреди
      широкого экрана без опоры.
- [x] **Карточка сервера говорит о том, что меняется.** Была: ядро, порт, RAM —
      три вещи, которые не меняются никогда, и ни одного действия. Стала:
      игроки, нагрузка, память, график CPU и кнопки запуска прямо на карточке.
      Ради этого `GET /servers` научился отдавать метрики по запросу
      (`metrics=1`) — до этого их считала только страница одного сервера, и
      карточка честно рисовала прочерки у работающего сервера.
- [x] **Токены поверхностей** — `--bg-sunken`, `--bg-hover`, `--bg-active`,
      `--accent-bg`, `--shadow`, `--shadow-lifted`. Все пять тем обновлены, все
      новые пары внесены в контрастный тест: поверхность, которой нет в
      списке, — это поверхность, которую никто не проверяет.
- [x] **Иконки** — свои инлайновые SVG. Не пакет: панель отдаётся демоном под
      строгим CSP, и шрифт или спрайт с CDN просто не загрузился бы.
- [x] **Память делится на настоящий потолок.** Контейнеру выдаётся heap плюс
      запас, и деление использования на heap показывало здоровый сервер вышедшим
      за лимит (4.2/4.0 ГБ). Рантайм теперь отдаёт свой предел
      (`metrics.ram_limit_mb`). Заодно в спеке поле метрик называлось
      `memory_mb`, а API отдавал `ram_used_mb` — расхождение исправлено.
- [x] **Консоль возвращается после перезапуска демона.** Буфер живёт в памяти,
      поэтому обновление панели (то есть перезапуск службы) оставляло у
      работающего сервера пустую консоль. Docker логи хранит: при усыновлении
      контейнера буфер заполняется из `docker logs`. Первая попытка читала
      сокет сырьём, как attach, и молча получала chunked-мусор — консоль
      оставалась пустой, а всё выглядело успешным.

## Релей

Сделано 2026-08-11 по вопросу пользователя «можно ли автоматизировать Hamachi
и Radmin». Ответ: их — нет. У Radmin VPN нет ни CLI, ни API; у Hamachi CLI
есть только под Linux, установщик проприетарный, и даже при полной
автоматизации своей стороны друг всё равно ставит клиент и вступает в сеть
руками — а автоматизировать чужую машину панель не может.

Автоматизировать можно саму задачу. Выбран релей, а не ZeroTier и не
playit.gg: playit делает панель зависимой от чужого аккаунта и чужого домена,
ZeroTier требует поставить на хост сетевой драйвер и всё равно оставляет другу
установку приложения. Релей — единственный вариант, где не ставит **никто,
кроме владельца панели**.

- [x] **`cmd/mirocraft-relay`** — отдельный бинарник: он живёт на другой
      машине и делает другую работу. Токены хранит только хэшами, как и всё
      остальное в проекте.
- [x] **Протокол** — построчный, с обратным дозвоном: на каждого игрока агент
      открывает отдельное соединение вместо мультиплексора поверх
      управляющего. Мультиплексор — это кадрирование, управление потоком и
      блокировка головы очереди, а игроков десятки, а не десятки тысяч.
- [x] **Пиннинг сертификата** для релея с самоподписанным. Через
      `VerifyConnection`, а не `VerifyPeerCertificate`: второй не вызывается
      при возобновлении сессии, то есть пиннинг обходился бы.
- [x] **Найдено живой проверкой:** `SetDeadline` в рукопожатии ставит дедлайн
      и на запись тоже, а снимался он только с чтения. Через десять секунд
      запись в управляющее соединение протухала, и первый же игрок ронял
      туннель. Тесты этого не видели, потому что тестовый игрок приходит через
      миллисекунды; теперь таймауты — переменные, и тест ждёт дольше дедлайна.
- [x] **Проверено через настоящий интернет:** Paper 1.21.4 на домашней машине
      за NAT, релей на машине с белым адресом, пинг снаружи — 400 мс.

## Найдено на живой машине

**Windows Server 2022** (2 ГБ, 1 ядро) — прогон 2026-08-10.

- [x] **Команда установки под Windows из README не работала вообще.** BOM в
      начале файла ломает `irm | iex`: строка не должна начинаться с U+FEFF,
      иначе `<#` не распознаётся и весь комментарий читается как код. А без
      BOM PowerShell 5.1 читает .ps1 в системной ANSI-кодировке, и кириллица
      бьётся так, что скрипт не парсится. Одним файлом эти два требования не
      выполнить, поэтому их два: `install.ps1` — чистый ASCII-загрузчик без
      BOM, `panel.ps1` — установщик с BOM. Проверено, что ни перевод строки,
      ни пробел, ни однострочный комментарий после BOM не спасают.
- [x] Первая починка тоже не работала: загрузчик дописывал второй BOM поверх
      скачанного. Вторая тоже: `Invoke-WebRequest` отдавал строку,
      декодированную не в той кодировке. Теперь скачивание идёт байтами прямо
      в файл, без единого шага декодирования.
- [x] **Служба не создавалась.** Путь по умолчанию `C:\Program Files\Mirocraft`
      содержит пробел, строка запуска поэтому в кавычках, а PowerShell 5.1
      экранирует их при передаче в нативный exe так, что `sc.exe` печатает
      справку и возвращает 1639. Заменено на `New-Service`. Тест этого не
      ловил, потому что ставил в каталог без пробелов — теперь с пробелом.
- [x] **Порт сервера не открывался в фаерволе.** Сервер слушает, панель
      показывает «работает», игроки подключиться не могут, в журнале чисто.
      Появился `internal/firewall` за интерфейсом: Windows Firewall через
      netsh, ufw и firewalld — на Linux. Открывается при старте, убирается при
      удалении сервера; выключенный фаервол панель не включает.
      Тест сразу нашёл в нём ошибку: `firewall-cmd --state` при выключенном
      фаерволе печатает `not running`, а проверка искала подстроку `running`.
- [x] Уборка в самом тесте установщика удаляла службу, не остановив её:
      `sc delete` только помечает, файлы остаются заблокированными, каталог не
      удаляется, и следующий прогон молча уходил в ветку обновления — то есть
      проверял не то, что заявлено.

**Работает на Windows Server:** установка одной командой, сверка контрольной
суммы, служба под SCM, панель по HTTPS из интернета, скачивание Java 21 на
хост, Paper 1.21.4 нативным процессом через ProcessRunner, консоль, `auto_start`
после настоящей перезагрузки машины.


Отдельно от фаз, потому что нашлось не по плану, а на арендованной VPS
(Ubuntu 24.04, 2 ядра, 2 ГБ) — там, где только и можно было найти.

- [x] `auto_start` и `auto_restart` хранились, показывались в панели и **ничем
      не обрабатывались** — как `max_disk_mb` до аудита. Обнаружилось
      перезагрузкой машины: панель поднялась, сервер остался лежать, хотя
      галочка стоит. Теперь демон на старте поднимает помеченные серверы —
      по очереди, а не разом, потому что четыре JVM, берущие свою кучу
      одновременно, кончаются тем, что машина убивает одну. А упавший сервер
      поднимается снова, если владелец просил: только на падение, не на
      остановку оператором, и не больше трёх раз за десять минут — цикл
      падений хуже лежащего сервера.
      Проверено на машине: полная перезагрузка → панель, сервер и приём игроков
      снаружи вернулись сами; `docker kill` → сервер поднялся за 6 секунд.
- [x] И сразу же мой собственный баг в этой починке, который не поймал ни один
      юнит-тест: обнуление счётчика попыток стояло в `startServer`, через
      который идёт и автоперезапуск, — то есть он обнулял собственный лимит.
      Четыре убийства подряд дали четыре перезапуска вместо трёх. Обнуление
      перенесено в обработчик power, где старт означает чьё-то решение;
      добавлен тест, который идёт тем же путём, что автоперезапуск, а не через
      эндпоинт.

- [x] 7.3 Документация: docs-сайт, публикация docs/API_GUIDE.md как раздела «API»
      с проверкой всех примеров curl на живой панели.
